# 選項 FS（改 Flux 的排程）驗證第 1、2 步的結果（2026-10-30）

數字、錨點、每條預測對錯：`results/topic/analysis.txt`（FS 節）；表格：`results/topic/fs1_v1/fs1_table.md`、`fs1b_v1/fs1b_table.md`；文獻：`results/topic/fs_literature_20261030.md`。全部 guard CLEAN、Flux 輸出正確。未經 auditor。

## 結論

**差距是真的、不是選設定的問題、也不是硬體互搶——問題在 Flux 自己的機制裡，原則上可以用軟體修。** 但「是 Flux 的哪一部分造成」還沒找到，要第 3 步（在 kernel 裡打時間戳，需要重編 Flux）才知道。

| 問題 | 實驗 | 結果 |
| --- | --- | --- |
| 換成最好的設定就好了嗎？ | FS1：Flux 內建 `profiling()` 試遍 64 種設定 | 不行。M ≤ 2048 時最佳設定仍是理想的 **1.35×**（預設 1.49×，最多 1.62×），只拿回 29% |
| 別人做了嗎？ | 文獻（親讀 Syncopate） | 部分。Syncopate（OSDI'26）在 **H100** 上「依到達順序排計算＋自動調參」，平均是 Flux 等最佳手寫的 104%；**沒有 A100、沒有小 M 對 Flux 的數字**。沒有人在 dense AG+GEMM 用「依資料是否到達動態分派」 |
| 是不是硬體互搶（別篇論文的說法）？ | FS1d：完全不用 Flux，copy engine 搬資料＋cuBLAS 同時跑 | **不是**：搬運 0.91–1.00×、GEMM ≤ 1.05×，兩者能完全重疊 |
| 那 Flux 的通訊和計算同時跑呢？ | FS1b / FS1c | 只有 Flux 的 all-gather 會被拖慢（中位數 2.8×）→ 原因在 Flux 的做法（每次開頭的跨卡屏障 kernel、每塊的旗標寫入、拉取方向、每個 tile 的系統層級等待；還沒拆開） |

事前登記的判定：FS1 成立；文獻「部分已做」；FS1b/c 的「≤ 1.15」**形式上未過**（1.28–1.30×），但 FS1d 證明那個測試量到的是 Flux 自己的 all-gather 路徑、不是硬體 → 依補充 3 的規則，屬「互搶未成立，要第 3 步才能判定」。

## 能拿到多少（推論）

- 硬體上，M ≤ 2048 的 all-gather＋GEMM 可以做到接近 max(通訊, 計算)；現在 Flux 最佳設定是它的 1.35×（中位數）→ 單一運算可望快約 **1.3×**（最多約 1.5–1.6×，通訊受限的 QKV 層）。
- prefill（chunked prefill 512–2048 token）端到端可望比現在的 Flux 快約 1.15–1.25×（推論，未量）；再疊 Flux 本來就比 vLLM 預設快的 7–20%。
- 比題目 T（整步 1.09×）明顯，接近使用者要的「明顯提升」，但**前提是第 3 步找得到原因並修得掉**。

## 風險

1. 原因找不到或修不掉（例如是 copy engine 拉取方向本身的限制；FS1d 用推送，Flux 用拉取，尚未比較）。
2. 新意：審稿會拿 Syncopate 比；要說清楚「A100、小 M、原因拆解、動態分派」是它沒做的。
3. 工程量：改 Flux 的 CUDA／CUTLASS 程式並重編（`build.sh --arch 80`；編譯時間未知）。

## 下一步（待使用者同意）

第 3 步（約 2–3 天）：先用不重編的方式拆原因（推送 vs 拉取、拿掉每次的屏障、旗標寫入方式），再重編 Flux 在 kernel 內打時間戳，看每個 tile 等了多久、資料何時到；
事前登記：找出佔差距一半以上的原因，且一個簡單修改（原型）在 M = 512–2048 讓中位數比現在快 ≥ 1.15× → 確定做 FS。

## 第 3 步結果（2026-10-30 深夜，`20261030_fs_step3_plan.md`）

- **原因拆解**：E1 顯示「同時跑」的測試本身會把部分 all-gather 卡在 GEMM 後面，不可信；改看 fusion-dispatch 既有的 nsys（真實融合執行）：
  融合中的通訊幾乎沒變慢（+0–20%）→ 硬體互搶再次排除；但最後一份資料到達後，GEMM 還要跑很久（L-QKV M=2048：211 µs）。
- **第一個原型失敗**：把 stream-K 的「多個 SM 合作」區段從最先到的資料移到最後到的資料（環境變數開關，預設關閉時與修改前逐位元相同 192/192）。
  30 個點中只有 3 個點真的改到（其餘的設定根本沒有合作區段），而且那 3 點變慢（0.84–0.91×）；中位數 1.00× → 依事前規則（< 1.05×）**這個原型不成立**。
- **修正後的推論**：小 M 時一個 tile 在一個 SM 上要約 150 µs，資料每約 36 µs 到一份 → 最後到的那份至少還要一個 tile 的時間，順序怎麼排都一樣。
  要縮短得把「最後到的 tile」拆給很多 SM（強制 split-K）或用更小的 tile——要改 CUTLASS stream-K 的切分，比這次深，成效未知。
- **待使用者決定**：(a) 限時（約 2 天）再做一個原型（最後一份資料強制 split-K／小 tile），事前登記 ≥ 1.15×；(b) 停 FS，改驗證 M；(c) 回 T 或 F。
