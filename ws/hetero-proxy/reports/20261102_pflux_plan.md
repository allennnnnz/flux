# 方向 A「PCIe 版 Flux」的做法（計劃，2026-11-02，待使用者同意）

本文件沒有新量測。所有預估標「推論」，第 1 週的驗證會逐項確認。

## 1. 目標

在 GPU 之間**沒有 P2P、只能經主機記憶體**的 PCIe 上，讓 TP 的通訊和 GEMM 以 tile 為單位重疊，並把搬運本身變快。
實驗平台是 css-host-158 的「只走 PCIe 模式」（`results/pcieonly/check_v1/`，NCCL busbw 7.4–7.6 GB/s）。
我們的程式只用「GPU ↔ 主機記憶體」的 copy，物理上只經過 PCIe。每次量測都要讀 NVLink 計數器，確認增量為 0；hxb 已用同一方法驗證過（STATUS 10-14）。

## 2. 架構（三個元件）

### 2.1 搬運層：取代 NCCL 的經主機路徑

**All-gather：上傳一次，大家下載。**

```
GPU j：自己那份切成塊 → copy engine 上傳到主機（本地 NUMA）→ 每塊寫一個主機計數器
GPU i：stream 等計數器 ≥ 本輪值 → copy engine 下載那一塊 → 寫 GPU 上的旗標
```

- NCCL 的經主機環狀做法：每卡每一步都要上傳和下載，兩個方向同時擠。
- 我們的做法：每卡上傳 1/8，下載 7/8，流量幾乎都是單向。
- 頻寬預估：M0 量到 8 卡同時下載時每卡 10.7 GB/s，NCCL 是 7.6，約快 1.4×（推論）。
- 可調的地方：
  - 下載順序依交換器與插槽錯開。
  - 跨插槽的那幾份是否在兩顆 CPU 的記憶體各放一份。
  - 塊的大小。
- 用到的機制：
  - stream memory op（`scripts/hxb/cudamem.py`），不需要主機執行緒。
  - hxb 已量過一次往返約 11 µs。

**Reduce-scatter：做法未定，第 1 週先量。** RS 天生是雙向的：每卡要送出 7/8 的部分和，也要收回 7/8。三種候選：

- (a) 直接經主機互送，只靠重疊。
- (b) CPU 幫忙加總：上傳多、下載少，但會吃主機記憶體頻寬。M0 量過這會互搶。
- (c) GEMM 每算完一批 tile 就觸發上傳（FlashOverlap 式），只靠重疊。

### 2.2 計算層：等旗標的 GEMM

- 直接用 hxb 的 `chunk_gemm`（`scripts/hxb/gpu_consumer.py`，Triton）。每個 tile 先等它那一塊的旗標，再開始算。
- 2026-10-09 量過一個形狀（4096×5120×5120，bf16）：這個 GEMM 0.912 ms，cuBLAS 0.919 ms。其他形狀要逐一對照 cuBLAS。
- RS 側的 GEMM 要多做一件事：一批 tile 算完就累加計數器，讓 copy stream 可以開始上傳那一批。

### 2.3 選擇器：沿用 fusion-dispatch 的成本模型

- 每一層依 (形狀, M, 連線種類) 選一個做法：NCCL 不重疊、NCCL 切塊重疊、我們的做法，或連線是 NVLink 時用 Flux。
- 預期 NVLink 模式選 Flux 或 NCCL，只走 PCIe 模式選我們的做法。這就是「簡單規則會選錯」的場景。

## 3. 端到端估算（推論，第 1 週 V1 會量）

設定：Qwen2.5-32B、TP8、prefill 4096 token。

- 每層 4 次大通訊（2 次 AG、2 次 RS，或等價的 2 次 all-reduce），每次 [4096, 5120] bf16 = 40 MiB。
- 只走 PCIe 時，NCCL 每次約 4.8 ms，每層合計約 19.3 ms。
- 每層計算約 2.3 ms（FC1 約 1.2、FC2 約 0.6，其餘小）。
- → **只走 PCIe 時，prefill 約 9 成時間在通訊。**

| 情況 | 每層約 | 對 NCCL 不重疊 |
|---|---|---|
| NCCL 不重疊 | 21.6 ms | 1.00× |
| 只有 AG 變快 1.4×、RS 不變、重疊藏掉計算 | 16.5–17 ms | 約 1.3× |
| AG、RS 都快 1.4× | 約 13.8 ms | 約 1.55× |

→ 端到端約 **1.3–1.55×**，落在哪一端取決於 RS 能不能也變快。

## 4. 第 1 週：驗證（只量搬運，不寫融合 kernel）

每次量測都包在 `common/measure/exclusive_guard_v2.py` 內，放在 tmux 執行。輪次打亂、比較對象交錯量；量不到 1 ms 的單位時用 GPU 端先墊等待；背景記錄 SM 時脈。

- **V1 上限**：在只走 PCIe 模式下，量 Qwen2.5-32B 四種層形狀：
  - M = 1024 / 2048 / 4096 / 8192 時的 NCCL AG / RS 時間；
  - 同樣形狀的 cuBLAS GEMM 時間。
  
  據此算出「只靠重疊」和「搬運變快 1.4×」兩種情況的上限，取代第 3 節的推論數字。
- **V2 AG 搬運**：寫一個「上傳一次、大家下載」的 all-gather（只用 copy engine 和計數器，不接 GEMM）。
  - 比較對象：NCCL 經主機 AG，在 SM 搬與 copy engine 搬兩種模式下各量一次。
  - 大小：5–80 MiB。
  - 變體：每份資料只放一顆 CPU 的記憶體或兩顆各放一份；下載順序是否依拓撲安排。
  - 錨點：單卡下載 21.3 GB/s、8 卡合計 85.4（`params.json` h2d_topology_m0）。
- **V2b RS 搬運**：量 2.1 節的 (a)、(b) 兩種 reduce-scatter 搬運方式，以及 8 卡同時上傳到主機的頻寬（T1 量到合計 101–104 GB/s，與 M0 的 85.4 對不上，這是未解的問題，要一起查清）。
- **判定規則**（量測前寫進 results，事後不改）：
  1. V2 在 20–40 MiB 時，我們的 AG 對 NCCL 經主機 AG 的 rank-max 中位數 ≥ 1.2× → 主賣點成立。
  2. 用 V1、V2、V2b 的實測數字重算第 3 節，prefill 大小的層 ≥ 1.3× → 進第 2 週。
  3. 規則 1 不成立 → 這個方向只剩「重疊」，上限約 1.25×（推論）→ 回報使用者，改做備案 B，或縮小成 workshop 規模。

## 6. 比較對象

| 基準 | 說明 |
|---|---|
| NCCL 不重疊 | 只走 PCIe 模式（SHM），先 AG 再 cuBLAS。主要分母 |
| NCCL＋copy engine | 同上，加 `NCCL_SHM_USE_CUDA_MEMCPY=1` |
| FlashOverlap（EuroSys'26） | GEMM 算完一批 tile 就呼叫 NCCL，不需要 P2P，程式支援 sm80。最直接的對手 |

## 7. 風險與退路

- **搬運沒有變快**（V2 < 1.2×）：第 4 節規則 3。
- **RS 沒辦法變快**：端到端落在約 1.3×（第 3 節）。論文仍成立，但幅度較小。
- **「用 A100 關掉 NVLink 來模擬」被質疑**：
  - 我們的路徑本來就只用 PCIe，用 NVLink 計數器增量為 0 證明；
  - 基準 NCCL 經主機的頻寬已和錨點對照過；
  - 有機器 B 更好。
- **Triton GEMM 在某些形狀比 cuBLAS 慢**：GEMM 單獨的時間兩者都報；分母用 cuBLAS，避免靠較慢的 GEMM 讓「重疊」看起來比較好。
- **與晶片的連結**：搬運層只需要「寫主機記憶體＋計數器」，hxb 的 CPU 後端與 A100 代理都已接上。論文最後可以加一節：其中一個 rank 換成 hxb 後端的示範（選做）。

## 8. 補充：用機器 B（gpu1，4× V100 PCIe）（2026-11-02，使用者問）

機器 B 的事實都出自 `ws/fusion-dispatch/reports/20261003_gpu1_inventory.md`：
- 4× V100-PCIE-32GB，sm70，fp16，沒有 bf16。
- 每卡 PCIe Gen3 x16，直接接在 CPU 上，沒有交換器。
- P2P 只在 GPU0↔1、GPU2↔3；跨 CPU 要經主機記憶體＋QPI。
- 共用機器，沒有 GPU 排程；`/` 只剩 9 GB。
- guard v2 已修正 gpu1 上的兩個誤判。

**比 158 好的地方**
- 真的 PCIe 機器，不用回答「模擬可不可信」。
- 連線混合：同一對卡有 P2P，跨對要經主機。拓撲感知可以做成「同對走 P2P、跨對經主機」。這也和將來的情境同構：GPU 之間有快連線，晶片只能經主機。
- 文獻調查沒找到任何論文在 Volta＋PCIe 上評估過。
- 通訊和計算的比例不同（推論）：
  - Qwen2.5-32B 每層 GEMM 約 4.2 TFLOP（M=4096）。
  - 158 只走 PCIe 時，計算約 2.2 ms（TP8），通訊約 19 ms，大約 1:9。
  - V100 TP4 時，計算約 12 ms（以 90 TFLOPS 估），通訊約 12–20 ms（以 6–10 GB/s 估），大約 1:1。
  - 1:1 正是「重疊」最有用的區間，只靠重疊就可能接近 2×。
  - 兩台機器合起來，剛好涵蓋「通訊遠大於計算」和「兩者相當」兩種情況。
  - 如何驗證：在 gpu1 量 fp16 cuBLAS 與 NCCL TP4 的 AG / RS 時間。

**比 158 差的地方**
- Flux 與 FlashOverlap 都不能跑：Flux 只支援 sm80/89/90，FlashOverlap 的程式支援 sm80/86/89。最直接的對手只能在 158 上比。
- Triton 新版可能不支援 V100 的 tensor core（未確認；建環境時用 5 分鐘測 `chunk_gemm`）。如果不行，改成「stream 等到那一塊的計數器，再呼叫 cuBLAS 算那一塊」：粒度較粗，但任何 GPU 都能跑。
- 只有 4 卡（TP4）；fp16；Haswell CPU，主機記憶體頻寬可能成為經主機搬運的瓶頸（推論）。
- 共用機器：量測容易被污染，守衛中止的機率高，要排在沒人用的時段。
- 要在 gpu1 上另開 session 執行（10-03 的盤點就是這樣做的）；建環境約半天（盤點報告第 6 節）。

**建議**：主開發與主要比較仍在 158（可獨佔、8 卡、對手能跑、同一顆 GPU 切換連線種類）。V100 當第二平台，放兩次：
- 第 1 週加半天：在 gpu1 量 PCIe 錨點（單卡上傳 / 下載、同對 P2P、跨 QPI）、確認 Triton 能不能跑、量 NCCL TP4 的 AG / RS 與 fp16 GEMM，確認上面那個比例。
- 第 9 週：把單層與端到端實驗搬到 gpu1 重跑。

## 9. 補充：為什麼「上傳一次、大家下載」會比較快（2026-11-02，使用者問）

前提是沒有 P2P：資料只能「上傳到主機、再從主機下載」。但變快的原因不是 P2P 本身，而是本機量到的一個不對稱現象。

**單一張卡同時上傳和下載時，它的下載會掉到約 1/3，上傳不受影響。**

| 情況 | 下載速度（GB/s） | 上傳速度（GB/s） |
|---|---|---|
| 只有下載 | 22.01 | — |
| 同時上傳 | 6.46 | 22.52 |

- 來源：`params.json` pcie_bidirectional，Phase 0 BIDIR_CORRECTION X.3，nsys 逐筆分類；nvbandwidth 獨立量到 8.88。
- I2（10-14）再量一次：同卡雙向時下載 5.95–7.3。
- 位置在卡本身：GPU0 只送、GPU2 只收時，兩邊互不影響（STATUS 10-14）。

**環狀傳法（NCCL 經主機）**：每一步，每張卡都要把資料傳給下一張（上傳），同時收上一張傳來的（下載）。所有卡全程都在「同時上傳和下載」的狀態，下載一直被壓在 1/3。
- Phase 0 自己寫的經主機環狀傳法：每卡 5.87 GB/s，是上表 6.46 上限的 91%；照交換器排順序也沒有改善（5.20）。原因是「每張卡都既送又收」（`params.json` staging.ring8_per_gpu_GBps）。
- NCCL 只走 PCIe 時 busbw 7.4–7.6，也落在這個量級（推論：受同一個限制）。

**上傳一次、大家下載**：每張卡先把自己那份傳上去，只有 1/8，以 22 GB/s 計約 0.2 ms（40 MiB 的 AG）；之後只剩下載。
- 只下載時，限制改成「共用的線」：一個交換器兩卡共用約 25 GB/s，一個插槽四卡共用約 42 GB/s。8 卡同時下載時，每卡 10.7（M0）。
- 環狀傳法裡，GPU0 的資料要被轉手 7 次，上傳 7 次、下載 7 次；新做法只上傳 1 次，總上傳量從 7/8 降到 1/8。

**還沒驗證的部分（V2 要量）**：
- 10.7 vs 7.6 是兩個不同實驗的數字，不是同一個 all-gather 的實測。
- 上傳和下載仍可能有一小段重疊，要排成「先傳自己那份、再開始下載」。
- V100 上有沒有同樣的不對稱，未知。

**相近做法（新意的界線）**：
- CPU 的 MPI 共享記憶體集合通訊早就用「公告欄」式做法。
- ThunderEP（2609.40093，只讀摘要）在 PCIe 消費級 GPU 上，把主機記憶體當共用媒介，做 MoE 的 all-to-all。
- → 招數 1 單獨不算全新。我們的貢獻要放在「TP 的 AG / RS＋tile 級邊收邊算＋避開這個不對稱的排程」的組合上。
