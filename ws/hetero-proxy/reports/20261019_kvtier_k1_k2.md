## 0. 一頁摘要

**要解的問題**：多人多輪聊天時，GPU 記憶體放不下所有對話的 KV cache（對話記憶）。現有系統（vLLM / SGLang 預設）把最久沒說話的人的 KV 丟掉，
他回來時整段重算（recompute prefill）：他自己等很久，重算也佔住 GPU，拖慢其他所有人。

**機制**：每輪結束時把新產生的 KV 存到 PCIe 另一端的記憶體（現在是 CPU 主記憶體）；被丟掉的人回來時經 PCIe 一層一層搬回，
第 i 層一到 GPU 就開始算第 i 層（每層一個到貨旗標，GPU 在 CUDA graph 內自己等，CPU 不介入）。

| # | 結論 | 證據 | 把握 |
| --- | --- | --- | --- |
| 1 | 搬回後的計算與 KV 一直留在 GPU **逐位元相同** | §4.4、§5.5 | 高 |
| 2 | 單一請求：搬回比重算快 **3.6×（1k 歷史）–19.4×（32k）**；保守估計（重算換算到全速時脈）3.6–17.8× | §4.3 | 高 |
| 3 | 8k 以下搬運完全藏在新一輪的計算底下（只比 KV 沒被擠掉多 1.5–7 ms）；16k 以上由 PCIe 決定（8 卡同時每卡約 10 GB/s） | §4.3 | 高 |
| 4 | 多人服務、輕負載（96 人搶 24 格）：首字中位數 **66.2 → 30.8 ms（2.15×）**，幾乎追平「記憶體無限」的 29.4 ms；吞吐量只 +1.7% | §5.7 | 高（限這組參數） |
| 5 | 多人服務、重負載（192 人搶 32 格）：重算佔 GPU 28%、連鎖惡化成排隊；外存首字中位數 **1239 → 35 ms（35×）**，吞吐量 **+7.5%** | §5.8 | 高（限這組參數） |
| 6 | 外存的天花板：只能幫「閒置中」的對話騰空間；正在生成的對話的 KV 必須在 GPU 上 → 重負載時外存最慢 10% 仍要等約 0.5 s（排隊等格子，不是搬運慢） | §5.8 拆解 | 高 |
| 7 | Cake（GPU 重算前段、PCIe 搬後段）在這台機器上全面變慢 | §4.3 | 高（限這台機器、這個模型） |

**不能說的**：KV 外存本身不是新發明（vLLM swap、LMCache、SGLang HiCache、CachedAttention 都做過）；ShareGPT 對話短，輕負載下絕對差距只約 35 ms；
GPU 容量是縮小版；只測了一個模型；未經審查。詳見 §7、§8。

## 1. 背景與問題

### 1.1 為什麼是 KV 外存

研究方向：讓只能經 PCIe 連接的非 NVIDIA 裝置加入 8 卡 NVLink 環境並帶來加速。之前已證明「能協同」（hxb 介面、E2E B）但沒有加速；
P1（`results/hetero_roles/p1/analysis.txt`，2026-10-15）篩選主流異質角色後，CPU 替身在算力型角色上無用（attention 外放 ≤ 0.5%、做 decode +1.8%），
在記憶體型角色上有用。使用者（2026-10-16）決定外部裝置只用 CPU、先在本機做出加速，選 KV 外存。

### 1.2 KV cache 是什麼、多大

模型讀過每個字後，在每一層算出該字的 Key 與 Value 向量，後續生成要用到前面所有字的 K / V。它是**算好的結果**，不是原始文字。
Qwen2.5-32B-Instruct：64 層、8 個 KV head、head 維度 128、bf16。TP8 下每張 GPU 持 1 個 KV head：

| 每個 token | 每張 GPU | 8 張合計 |
| --- | --- | --- |
| KV 大小 | 64 層 × 1 head × 128 × 2（K、V）× 2 B = **32 KiB** | 256 KiB |
| 8k token 的對話 | 256 MiB | 2 GiB |
| 原始文字（token 編號） | — | 約 32 KB |

扣掉權重（每卡約 8 GB），每卡約可放 200 萬 token 的 KV（推論，由大小換算）。

### 1.3 現有做法與它的代價

GPU 記憶體滿時，系統丟掉最久沒說話的人的 KV（只剩原始文字）。他回來時必須把整段文字重新過一遍模型，才能拿回 KV（重算）。
代價有二：他自己的首字時間變長；重算佔住 GPU，其他正在接收回答的人一起被卡住（本報告 §5 實測這兩者）。

## 2. 機制設計

### 2.1 資料流

```
每輪結束（存出，write-through）
  GPU KV cache ──D2H（copy engine）──> 主機記憶體（每卡自己的區域，NUMA 本地）
                 只存這一輪新增的 token

被擠掉的人回來（搬回）
  主機記憶體 ──H2D 第 1 層 K、V──> GPU，寫旗標[1] = 1
             ──H2D 第 2 層 K、V──> GPU，寫旗標[2] = 1   ...
  GPU（新一輪 prefill，CUDA graph）：第 i 層算完 QKV 後，等旗標[i] ≥ 1 才做 attention；graph 結尾把旗標歸零
```

### 2.2 設計細節與來源

| 設計 | 做法 | 借鑑 / 理由 |
| --- | --- | --- |
| 逐層搬回、邊搬邊算 | 第 i 層搬完即可算第 i 層的 attention | LMCache（layerwise）、SGLang HiCache、CachedAttention（ATC 2024） |
| 每層一個到貨旗標 | 搬運 stream 用 `cuStreamWriteValue64` 寫旗標；graph 內用 `cuStreamWaitValue64` 等；兩者都錄成 graph 節點（2026-10-16 探針確認） | **Flux 的精神**：Flux 的 GEMM tile 等自己的旗標、資料一到就算（Flux 原始碼 `src/coll/ths_op/all_gather_op.cc` 用的就是 CUStreamWriteValue）；本機制把單位從 tile 換成層、鏈路從 NVLink 換成 PCIe |
| copy engine 搬運 | `cuMemcpyAsync`，不佔計算核心 | 調查報告的 ConCCL 觀察（HiCache 預設用 GPU kernel 搬，佔 SM） |
| TP 分片各搬各的 | 8 卡同時各搬自己 1 個 KV head 的分片，8 條 PCIe 並行 | 自行量測決定 |
| 主機記憶體 NUMA 本地 | GPU0–3 的區域放 node 0、GPU4–7 放 node 1（以該節點的 CPU 首次寫入定位，`/proc/self/numa_maps` 驗證） | 自行量測決定 |
| 主機佈局 | `[層, K|V, token, 128]`：每層的 K（或 V）一段連續記憶體 → 每層每卡兩次連續拷貝 | 避免 HiCache 那種分頁零散拷貝 |
| 只存新增 | 每輪結束 D2H `[已存長度, 目前長度)` | HiCache 的 write-through 策略 |
| 搬 vs 重算 vs 兩者並用 | 實測後一律搬（§4.3） | Cake（ICML 2025）評估後否決 |

### 2.3 誠實評估：哪些是新的

核心想法（把 KV 存到主記憶體、逐層搬回）**不新**，最接近的是 CachedAttention 與 HiCache。本機制的差異（Flux 式旗標在 graph 內、copy engine、
TP 分片並行、逐位元正確）讓實作更有效率，但沒有帶來它們做不到的新能力。另須說明：K1 / K2 中 CPU 只是被動的倉庫（GPU 主動拉資料），
hxb 的 CPU 後端程序（獨立 DMA 引擎）沒有用上，用上的是 hxb 的 stream memory op 旗標。研究上可能的新意在後續方向一（K4：搬運與 TP all-reduce 的干擾排程）。

## 3. 實作

### 3.1 推論程式

自寫的 Qwen2.5-32B-Instruct TP8 推論程式（`scripts/e2e/qwen_tp_v1.py` → `v5`）：真實權重；每層 QKV / O / gate-up / down 依 Megatron 方式切成 8 份，
O 與 down 後以 NCCL all-reduce 加總；融合 Triton kernel（add+RMSNorm、RoPE+KV 寫入、split-K decode attention、silu·up，`scripts/e2e/fused_kernels.py`）。
不用 vLLM 的原因：本機未安裝，且無法在每層之間插入「等第 i 層搬到」的檢查點。

| | K1 程式 | K2 程式 |
| --- | --- | --- |
| 檔案 | `scripts/kvtier/kvtier_v5.py` | `k2_engine_v1.py`、`k2_kernels.py`、`k2_serve_v1.py` |
| KV cache | 一個序列（slot 0），最長 32768 | 固定格子 `[層, 格子數+1, 1, 4608, 128]`（多 1 格給補齊用的假列），初始化為 0 |
| CUDA graph | 每種形狀一個：新一輪（T, P）、重算（P+T）、Cake 的重算段 | 110–111 個：decode 依批次大小（1–48）、新對話 / 重算依長度（16–4096）、接續依「新句長度 × 歷史視窗（每 512 一級）」；歷史長度與格子編號從 GPU 記憶體讀，一個 graph 服務所有同級長度 |
| 新一輪的 attention | SDPA + `causal_lower_right` 遮罩 | 重算：SDPA flash（causal）；接續：GPU 上依 P 算遮罩 + SDPA（mem-efficient） |
| decode | v5 的 graph | slot 對照表版 kernel（每列讀自己的格子，`test_k2_kernels_v1.py` 驗證與原版逐位元相同） |
| all-reduce | graph 用獨立 NCCL communicator、固定輸出緩衝區 | 同左 |

速度的合理性：重算 8192+128 token 用 450 ms，以 FLOP 數換算約達 A100 bf16 峰值的 50%（推論；如何驗證：同形狀與 vLLM 實測對照，未做）。
三種做法共用同一程式，只差「被擠掉的人回來時怎麼辦」，比較不受絕對速度影響。

### 3.2 正確性驗證方法

- 參考答案：`scripts/kvtier/hf_reference_kv_v3.py` 從 ShareGPT 挑三段真實多輪對話（接回被切開的段落），用 HuggingFace 官方實作（transformers 4.49、torch 2.6、單卡 bf16）
  讀「歷史 + 新的一句」後貪婪生成 64 字，並記錄每一步前兩名 logit 的差距（判斷分歧是否在平手處）。

  | 項目 | 對話 id | 歷史 P | 新的一句 T | HF 自己前兩名差 ≤ 0.125 的步數 |
  | --- | --- | --- | --- | --- |
  | hist2k | QWJhYvA（第 10 輪） | 1639 | 21 | 4 / 64 |
  | hist4k | X1KM796（第 4 輪） | 3590 | 31 | 1 / 64 |
  | hist8k | SyboCvP（第 6 輪） | 8354 | 40 | 2 / 64 |

## 4. K1：單一請求

### 4.1 問題

一段對話的 KV 已被擠出 GPU，使用者回來說一句新的話（128 token）。量**請求開始 → 第一個回答字的 logits 算出**（首字時間），比較各種做法。

### 4.2 方法

- 程式：`scripts/kvtier/kvtier_v5.py --mode bench --rounds 200`，經 `run_bench_v1.sh`（同時以 `nvidia-smi -lms 200` 記錄 SM 時脈）
- 結果：`results/kvtier/bench_v5/`（`bench_kvtier_v5.json`、`clocks.csv`、`analysis.txt`）；分析 `scripts/kvtier/analyze_bench_v2.py`
- 日期：2026-10-16 08:16–08:41 UTC；guard：**CLEAN**（1 筆 SELF_CPU 警告：自己帳號的一個程序在 08:36 短暫 58.7% 單核）
- 歷史 P ∈ {1024, 2048, 4096, 8192, 16384, 32000}，新的一句 T = 128。計時用的 token 是隨機的（計算量只看長度），正確性另驗（§4.4）
- 每個案例的定義：

  | 案例 | 做法 |
  | --- | --- |
  | 理想 ideal | KV 還在 GPU，只算新的一句（下限） |
  | 理想（eager） | 同上但逐個發 kernel（對照引擎開銷） |
  | 重算 recompute | 從位置 0 算 P+T 個 token（基準） |
  | 先搬完再算 serial | 搬完全部層才開始算新的一句 |
  | **邊搬邊算 layer** | 本機制 |
  | Cake split x | GPU 重算前 x·P 個 token，同時 PCIe 搬回其餘，再算新的一句（x = 1/16、1/8、1/4） |
  | 純搬回 load / 純存出 save | 只搬資料（每卡 GB/s，對照錨點） |

- 每輪把 60 個案例打亂（各 rank 同順序）交錯執行；每個案例前 barrier + synchronize，8 卡同時開始
- 每卡用 CUDA event 計時，每輪取 8 卡中**最慢**的（請求要 8 卡都完成），200 輪取中位數
- 主機上放 4 份歷史 KV 輪流使用（每卡 3.91 GiB，遠大於 CPU L3），避免從快取讀
- 時脈：每輪取視窗內 8 卡最低 SM 時脈，**逐案例**剔除低於該案例眾數 95% 的輪次（12000 輪剔除 1271）；
  另給保守版加速：重算時間乘以（該案例時脈 / 1410 MHz），即假設重算在全速時脈下跑
- 錨點：`results/e2e/c_diag`（8 卡同時 H2D 每卡 10.1–12.2 GB/s）

| G7 搬回 9–12、存出 9.5–12 GB/s | 搬回 8.5–10.7、存出 9.9–11.0 | 不成立（P = 1024 搬回 8.5，小拷貝的固定開銷） |

### 4.6 解讀

- **搬比重算便宜很多**：搬一個 token 的 KV（每卡 32 KiB，約 10 GB/s）約 3.3 µs，重算一個 token 約 54 µs（8k 時：450 ms / 8320 token），差約 16×。
- **8k 以下看不出被擠掉過**：搬運時間（≤ 26 ms）被新一輪的計算時間（約 21 ms）蓋住，邊搬邊算只比理想多 1.5–7 ms。
- **16k 以上由 PCIe 決定**：首字時間 ≈ 純搬運時間 + 約 2 ms。
- **Cake 在這台機器上沒用**：搬運本來就比重算快很多，讓 GPU 分擔只是多跑一趟；而且兩趟 graph 的固定成本（每趟約 20 ms）更讓短歷史吃虧。
  適用於搬運比重算慢的情況（較慢的鏈路、多人同時搬）。
- **引擎開銷的教訓**：逐個發 kernel 時，128 token 的新一輪要 49.5 ms（graph 20.1 ms）；v1 / v2 的試跑量到的是 Python 發 kernel 的速度。

## 5. K2：多人服務

### 5.1 問題

很多人同時多輪聊天、GPU 只放得下部分對話的 KV 時，外存能讓整個服務快多少？背景存出會不會拖慢正在生成的人？

### 5.2 工作負載

- 使用者資料：`scripts/kvtier/k2_trace_v1.py` → `results/kvtier/k2/users_v1.json`。3000 段 ShareGPT 多輪對話（接回連續段；至少 2 輪；總長 ≤ 8128），
  其中總長 ≤ 4096 的 2997 段可用（格子長度限制）。
- 統計：平均 4.5 輪；整段對話總長中位數 1509、90% 2205、99% 2452 token；每輪新說的話中位數 24、90% 80 token；回答長度中位數 240、平均 250 token。
  **ShareGPT 經資料集清理後偏短**（刪掉的段落使接回只能停在缺段前），報告結果時須說明。
- 每輪的輸入：第 0 輪 = 預設 system prompt + 第一句（chat template）；第 k 輪 = 模型上一輪回答之後接的
  `<|im_end|>\n<|im_start|>user\n{第 k 句}<|im_end|>\n<|im_start|>assistant\n`。
- 回答長度固定為資料集中該輪回答的 token 數（夾在 16–512）：模型生成的內容是自己的，但長度固定 → 三種做法的工作量完全相同。
- 使用者行為（封閉迴圈）：送出 → 等回答完 → 思考 Exp(平均 30 s，依 座位 / 對話 / 輪次 固定亂數種子) → 下一句；對話結束後該座位開始下一段對話。
  座位 i 依序服務第 i、i+N、i+2N… 段對話，各做法完全相同。
- **GPU 格子**：一格 = 一段對話的 KV（最多 4608 token）。輕負載 96 人 / 24 格，重負載 192 人 / 32 格。這台機器以這種格子可放約 400 格（推論：每格每卡 4608 × 32 KiB ≈ 151 MB，每卡約 65 GB 可用；理想做法 192 格時 GPU 已配置 37.7 GiB），
  縮小容量是為了用較少的模擬使用者製造記憶體不足、在合理時間內跑完（**縮小版，須說明**）。

### 5.3 推論程式與排程

- 程式：`k2_engine_v1.py`（§3.1）、`k2_serve_v1.py`。rank 0 決定每一步要做什麼（排程計劃經 gloo 廣播），8 卡執行同一計劃。
- 每一步（iteration）：最多處理一位新來的人的 prefill，然後所有正在接收回答的人一起 decode 一個字（含剛 prefill 的人）；每步結束同步一次。
- 新來的人需要格子：自己的 KV 還在（命中，接著算新的一句）→ 否則用空格 → 否則擠掉**正在思考**的人中最久沒說話的那位；都沒有就排隊。
  挑選不採嚴格先來先服務：找第一個排得進去的人（嚴格先來先服務會卡死：排頭等格子，格子被排在後面、KV 還在的人佔著）。
- 三種做法（只差被擠掉的人回來時怎麼辦）：

  | 做法 | 被擠掉的人回來時 |
  | --- | --- |
  | 理想 ideal | 格子數 = 人數，永遠不會被擠掉（上限） |
  | **外存 tier** | 每輪結束把新增 KV 存到該座位的主機區域（每卡 12 GiB / 24 GiB）；回來時逐層搬回 + 接續（K1 機制） |
  | 重算 recompute | 從位置 0 重算整段 |

### 5.4 量測方法

- 每次：暖身 180 s（不計），正式記錄 600 s；計入「到達時間在暖身之後且已完成」的輪次
- 每種做法 2 次，順序 理想 → 外存 → 重算 → 重算 → 外存 → 理想（`scripts/kvtier/chain_k2_v1.sh`）
- 每次在 guard 內執行，同時記錄 SM 時脈與功耗（`run_k2_v1.sh`；服務量測報告時脈而不過濾：持續負載的功耗上限就是部署狀態）
- 指標：

  | 指標 | 定義 |
  | --- | --- |
  | 首字等待（TTFT） | 使用者送出 → 第一個回答字產生 = 排隊等待 + prefill GPU 時間 |
  | 每字間隔 | 每一步的牆鐘時間（正在接收回答的人兩個字之間隔多久） |
  | 吞吐量 | 600 s 內生成的總字數 / 600 s |
  | GPU 時間分配 | 各類 prefill 與 decode 的 GPU 時間（CUDA event）佔比 |

- 分析：`scripts/kvtier/k2_analyze_v1.py`（→ `analysis.txt`）、`k2_decompose_v1.py`（→ `decompose.txt`，把首字等待拆成排隊 + 計算）

### 5.10 加速從哪裡來

## 7. 限制與待查

1. **新意有限**：KV 外存本身業界已有（§2.3）。
2. **對話偏短**：ShareGPT 搬回的歷史中位數約 690–710 token，輕負載下絕對差距約 35 ms，使用者幾乎感覺不到。長對話（文件問答、agent）收益大（K1：32k 省 1.86 s），但這份資料裡很少。
3. **GPU 容量是縮小版**，且格子固定長度（每格 4608 token，對話中位數約 1500）；分頁式 KV（vLLM）同樣記憶體能放更多對話。結果依賴人數、格子數、思考時間。
4. **只測一個模型**：Qwen2.5-32B 用 GQA，每 token 的 KV 小（每卡 32 KiB）；KV 較大的模型搬運成本更高。
5. **與真實系統的差異**：每步最多一位新來的人（vLLM 會切塊 prefill 並與 decode 混合）；回答長度固定；使用者是模擬的；未與 vLLM 實測對照速度。
6. **CPU 只是被動倉庫**：GPU 主動拉資料，hxb CPU 後端程序未使用。
7. **待查：背景存 KV 反而讓 decode 快 1.2–2.8%**（兩種負載、所有批次大小方向一致）。推論：有存出的那一步，前一步剛有人講完、CPU 多做了取字，GPU 空檔多一點；
   如何驗證：在隨機步插入假的存出、比較同一批次。另，K4.1（後續）量到持續的全速存出會讓 decode 慢約 145%，與此不一致；推論是 K2 每輪只存約 8 MB、只壓到少數幾層。
8. **未經 auditor 審查。**

## 8. 結論

**可以說**：
- 用 PCIe 另一端的記憶體（CPU 主記憶體）存放 GPU 放不下的 KV，結果逐位元正確；被擠掉的對話回來時比重算快 3.6–19×；
  多人服務的延遲大幅改善（輕負載 2.15×、重負載 35×，皆為首字中位數），重負載吞吐量 +7.5%。
- Flux 式「資料到了就開算」以層為單位跨 PCIe 有效：8k 以下搬運完全藏住。
- 外部裝置靠記憶體容量（而非算力）就能帶來加速；剩下的差距來自 GPU 記憶體對同時生成人數的限制。

**不能說**：我們發明了 KV 外存；使用者在一般聊天中會明顯感覺變快；這些倍數適用於其他模型、其他容量設定或分頁式 KV 系統；已經審查。

**後續**：方向一（K4）——背景搬運與 TP all-reduce 的干擾排程；K4.1 已量到背景全速搬運使 decode 慢 45–145%，Flux 式錯開可壓到約 3%（另見 STATUS §0）。
