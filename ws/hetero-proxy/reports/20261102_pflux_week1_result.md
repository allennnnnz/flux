# 方向 A「PCIe 版 Flux」第 1 週驗證結果（2026-11-02）

## 0. 一句話結論

> **補充（同日，§3.1）：基準換成最新的 NCCL 2.32.3 後，NCCL 本身快了 8–9%。AG 剩 1.30×，RS 打平（1.01×），單層上限 1.25×、不重疊 1.12× → R2 對最新版 NCCL 不通過。** 論文的基準應該用最新版 NCCL，所以下面用 2.21.5 算出的 1.35× 不能當主結論。

**收齊資料（AG）用「上傳一次、大家下載」快了 1.42 倍。加總部分結果（RS）原本比 NCCL 慢；改成「GPU 上傳、CPU 推下去」後快了 1.09 倍。** 用實測的零件推算單層時間：計算全部藏進通訊時，上限快 1.35 倍；完全不重疊也快 1.21 倍。最早登記的判定（只用 V2 的項目）是 1.29 倍、差一點沒過；補上 CPU 推送後依第二個事前規則通過。融合 kernel 還沒寫，端到端數字都還是推算。

所有量測：
- css-host-158，只走 PCIe 模式（NCCL 2.21.5，30 條連線全走 SHM）；
- 守衛全部 CLEAN，8 張卡 NVLink 計數器增量全為 0；
- 輪次打亂、比較對象交錯執行，rank-max 中位數；
- 未經 auditor。

## 2. 結果

### 2.1 收齊資料（AG）：快 1.42 倍

輸出 [M, 5120] bf16，時間單位 ms。

| M（大小） | NCCL 只走 PCIe | 上傳一次、大家下載 | 加速 |
|---|---|---|---|
| 1024（10 MiB） | 1.233 | 0.895 | 1.38× |
| 2048（20 MiB） | 2.460 | 1.736 | 1.42× |
| 4096（40 MiB） | 4.861 | 3.419 | 1.42× |
| 8192（80 MiB） | 9.718 | 6.782 | 1.43× |

數字取自 V2c，V2 同一項目的差距在 1% 內。

- 換算頻寬：NCCL 7.5 GB/s → 10.7 GB/s，**剛好等於 M0 量到的「8 卡同時下載」上限**（85.4 / 8）。也就是說，我們的 AG 已經跑到下載速度的天花板。
- 結果與 NCCL 逐位元相同。
- 預測對錯：
  - 預測錯：把每份資料在兩顆 CPU 各放一份，反而慢 11–12%。讓一半的卡跨插槽讀，比上傳兩次划算。
  - 預測對：先傳自己那份再下載（sep），和邊傳邊收（ovl）只差 0.3%。原因是自己那份只佔 1/8。

### 2.2 加總部分結果（RS）：原本更慢，改成 CPU 推下去後快 1.09 倍

輸入 [M, 5120] bf16，時間單位 ms。

| M | NCCL | GPU 自己上傳也自己下載 | GPU 上傳、CPU 推下去（2 執行緒） | 對 NCCL |
|---|---|---|---|---|
| 1024 | 1.272 | 1.457 | 1.202 | 1.06× |
| 2048 | 2.504 | 2.851 | 2.311 | 1.08× |
| 4096 | 4.970 | 5.717 | 4.578 | 1.09× |
| 8192 | 9.877 | 11.361 | 9.052 | 1.09× |

**為什麼 GPU 自己下載會變慢**：RS 每張卡都要送出 7/8、也要收回 7/8，兩個方向同時跑。V3 量到：8 張卡都同時上傳和下載時，每張卡的下載只剩 5.8–7.2 GB/s；只下載時是 11.0–12.6。V2 的 RS 每方向剛好 6.45 GB/s，和 Phase 0 的崩落錨點 6.46 一致。

**試過但沒用：改用 SM 搬（V3）。** nvbandwidth issue #53 在同型平台上回報「SM 雙向沒有崩落」。我們的 Triton 搬運 kernel 重現不出來：
- 單卡雙向最好只有 10.9 / 9.5 GB/s；
- 8 卡更差；
- CTA 越多，SM 上傳越慢，原因未查。

**有用：讓 CPU 把資料直接寫進 GPU（V3c，GDRCopy）。** 這是 HFReduce（SC24）的做法。

| 情況 | 下載（每卡） | 上傳（每卡） |
|---|---|---|
| 8 卡，CPU 推（每卡 2 執行緒）＋ GPU 上傳 | 9.8–10.0 GB/s | 9.4–10.9 GB/s |
| 8 卡，copy engine 兩個方向都跑 | 5.8–7.2 | 9.4–12.0 |
| GPU0 單卡，CPU 推＋ GPU 上傳 | 19.6（只推時 19.7） | 18.9 |

- 原因（推論）：CPU 推送對 GPU 來說是「被寫入」，不必由 GPU 發出讀取請求。
- 只推不上傳時，CPU 推送合計 80.7，比 copy engine 下載的 94.5 慢。所以 CPU 推只在「兩個方向同時跑」時才划算，正好是 RS 的情況。
- 單執行緒推送就有 14.1 GB/s（外部工具 gdrcopy_copybw：15.1 / 18.3）。預測的 4–10 錯了。
- 每卡 1 個執行緒時，RS 反而慢（6.42 ms），2 個最好。

### 2.3 各層 GEMM（cuBLAS，每卡 TP8 形狀，M=4096）

qkv 0.213、o_proj 0.127、fc1 1.019、fc2 0.530 ms，合計 1.889 ms。qkv 比用 FLOP 估的多 33%（N 只有 896，跑不滿）。

## 3. 判定

| 規則（事前登記） | 結果 |
|---|---|
| R1：AG 在 20、40 MiB 都快 ≥ 1.2× | **通過**（1.42×、1.42×） |
| R2（第一版，只用 V2 的項目）：單層上限 ≥ 1.3× | **不通過**（1.29×，因為 RS 沒有變快） |
| V3 規則：8 卡雙向每方向 ≥ 9 GB/s 才做 V2c | SM 不通過 → 依規則改試 CPU 推送 |
| V3c G4：8 卡、每卡 4 執行緒、雙向 ≥ 9 | 照字面差 0.1 GB/s 沒過（8.9）；每卡 2 執行緒通過（9.8 / 9.4）→ 用 2 執行緒做 V2c（偏離字面，已記錄） |
| R2（重算，加入 CPU 推送的 RS） | **通過**（上限 1.35×；不重疊 1.21×） |

M=4096 單層時間（ms）：

| 做法 | 時間 | 加速 |
|---|---|---|
| 基準：NCCL、不重疊 | 21.55（通訊佔 91%） | 1.00× |
| 我們，不重疊 | 17.88 | 1.21× |
| 我們，計算全部藏進通訊（上限） | 15.99 | 1.35× |

其他大小（M=1024–8192）都差不多：上限 1.33–1.35×，不重疊 1.17–1.21×。

**這是用實測零件推算的，不是端到端實測。** 融合 kernel 還沒寫，所以「計算藏進通訊」只是上限。prefill 端到端合理的預期約 1.2–1.35×（推論）。這比計劃第 3 節原本估的 1.3–1.55× 低：RS 只快了 1.09×，不是 1.4×。

### 3.1 換成最新 NCCL（2.32.3）當基準

同一套程式，以 LD_PRELOAD 載入 `~/opt` 的 NCCL 2.32.3（實際載入版本已用 `ncclGetVersion` 確認），200 輪，守衛 CLEAN。原始輸出：`results/pflux/v2c_full/analysis_shm_n232.txt`。

| M=4096 | NCCL 2.21.5 | NCCL 2.32.3 | 我們 | 對 2.32.3 |
|---|---|---|---|---|
| AG | 4.861 | 4.432 | 3.410 | 1.30× |
| RS | 4.970 | 4.611 | 4.571（CPU 推） | 1.01× |
| 單層上限 | — | 19.98 → 15.96 ms | | **1.25×** |
| 單層不重疊 | — | 19.98 → 17.85 ms | | **1.12×** |

- 我們自己的項目和 2.21.5 那一輪差距 ≤ 0.3%；變的只有 NCCL。
- 事前預測 N1：「2.32.3 頻寬仍在 6.5–8.5 GB/s」成立（AG 8.28、RS 7.96）；「AG 仍 ≥ 1.3×」差一點不成立（1.299×）。
- **怎樣才能回到 1.3× 以上（推論，未量）**：V3c 量到 CPU 推送時雙向每卡可維持約 10 GB/s，但這裡的 RS 實際只跑出 8.0 GB/s。損失來自兩處：要等第一整塊上傳完才開始推，以及推送執行緒是 Python 寫的。若 RS 能跑到 10 GB/s，對 2.32.3 的單層上限約 1.41×、不重疊約 1.25×。驗證方法：上傳切成小塊，讓推送提早開始；推送執行緒改用 C 寫。

## 4. 這對論文代表什麼

- **「上傳一次、大家下載」本身不是新的**：ThunderEP（2026）在消費級 GPU 上就是這樣做 AG / RS，prefill 最多快 1.66×。
- **我們這台機器（A100 HGX）多了一個 ThunderEP 平台沒有的問題**：一張卡同時上傳和下載時，copy engine 的下載會崩落。ThunderEP 刻意讓兩個方向同時跑來吃滿頻寬；在我們這種機器上，這樣做反而會撞上崩落（V2 的 RS 就是這樣慢掉的）。
- **我們的對策**：AG 用「先上傳再下載」，RS 用「GPU 上傳、CPU 推下去」。這是目前找到、前人沒做過的部分；文獻代理也沒有找到任何量化這個崩落的論文。
- 可能的新意（更新）：
  1. TP GEMM 的 tile 級邊收邊算（ThunderEP 是一份資料整份到了才算）；
  2. 不需要輪詢執行緒的 stream memory op（RS 的 CPU 推送除外）；
  3. 依平台的雙向特性選擇搬運方式（copy engine / CPU 推），這可以和決策器結合。

## 5. 限制與未解

- **單卡雙向的錨點對不上**：V3 量到 GPU0 單卡同時上傳和下載時，下載 12.6 GB/s；Phase 0 用 nsys 量的是 6.46，nvbandwidth 是 8.88，差了約 2 倍，原因未查。8 卡的數字（5.8–7.2）和 V2 的 6.45、Phase 0 的 6.46 一致。
- **順序保證**：這台 GPU 不支援「等待後強制刷新遠端寫入」，所以 CPU 推送的正確性靠「資料先寫、旗標後寫」的 PCIe 寫入順序。正確性檢查前會先清掉舊資料，結果誤差都在 bf16 捨入範圍內，但這不是正式保證。
- **推送執行緒是 Python 寫的**（ctypes 呼叫 GDRCopy），每卡佔 2 個 CPU 核心；改成 C 或用更細的分塊可能更快。
- **NCCL 版本**：只比了 pixi 內建的 NCCL 2.21.5。本機另有 2.32.3（它的 SHM 已移除 CE 模式），基準要再比一次。
- **還沒看 nsys 時間軸**：「先傳自己再下載」這類關於並行的說法沒有 profile 佐證；目前只用 sep / ovl 的時間差推論。
