Findings beyond the predictions
  F1 Interference is NOT a DRAM bandwidth cap. With g8 at n=1 the socket reads only 152-154 GB/s in total, below
     CPU alone (138) + DMA alone (~43) = 181 and below the read anchor 172. Both sides slow down although the memory
     bandwidth is not saturated. Inference: DMA reads raise memory latency for the CPU kernel, and the CPU's
     traffic delays the DMA reads (memory-controller / mesh / IIO queueing). How to verify: CPU read-bandwidth kernel
     at 8-28 threads with and without g8; DMA from a socket whose cores are idle vs busy.
  F2 Interference eats a large part of the gain: dsv3 n=1 ideal 1.31 -> 1.10, n=4 1.40 -> 1.24. A split scheduler that
     uses solo rates (Apex-style, 2610.23006, single GPU) would over-assign to the GPU path; the cost model must
     include interference.
  F3 The extra links are the gain: one link (g1, = a one-GPU system) gives 1.02-1.08 at n=1-4; four or eight links
     give 1.09-1.28. g4 (one GPU per switch) gets about 90% of g8's gain.
  F4 n dependence follows the CPU kernel: the more compute-bound the CPU side (larger n, or a heavier dequant such as
     int4), the larger the gain. Inference: kt-kernel's int4 path on this CPU (no AVX512_BF16, no AMX) is
     compute-heavier than this bf16 kernel, so Kimi-K2.6 int4 would sit between the n=1 and n=16 rows. How to verify:
     time kt-kernel RAWINT4 on the Kimi-K2.6 expert shape (7168 x 2048) on this machine.
Limits: GPU-side SwiGLU not included (~10 us per slice, inference); CPU kernel is P1's, not kt-kernel; synthetic
