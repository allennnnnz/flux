- **gpu 模式**：GPU 純執行時間，近似 CUDA graph 重放。
- **steady 模式**：同一項連發 16 次，每次用不同 weight，近似 eager 的一疊層。

## 0. 結論

1. **在這台機器上，decode 大小的 M 不開 Flux 明顯較快，四層都一樣。** M ≤ 512 時，NCCL all_gather + cuBLAS（B）
   在每一層、每一點、兩種模式下都勝過 Flux fused；唯一例外是 L-GU M=512，平手。
   B 所需時間是 fused 的 0.32–0.90 倍（L-QKV M=8 gpu：0.056 vs 0.160 ms）。
2. **切換點在 M ≈ 1024–3072，依層而定**（gpu 模式；steady 見第 1 節）：
   - G-QKV：M ≤ 2048 off，≥ 3072 fused，單調；
   - L-QKV：≤ 1032 off，2048 平手，≥ 3072 fused，單調；steady 在 1024/1032 已是平手；
   - G-FC1：≤ 1032 off，2048 fused，**3072 off**（斷崖），≥ 4096 fused；
   - L-GU：≤ 1032 off，其中 512/1024 平手；2048 平手，3072 fused，**4096 off**（斷崖），≥ 6144 fused。
3. **輸在哪。** M ≤ 512 時，fused 比 B 多出的 0.068–0.086 ms：
   - 約 75–90% 來自 **Flux AllGather 的固定成本**：8 筆 copy 在同一 stream 串行、兩次 barrier，
     約 0.1 ms 的下限；NCCL 只要 0.03–0.05 ms；
   - 15–45% 來自 **Flux GEMM 比 cuBLAS 慢**；
   - **overlap 只收回約 0.014 ms**。M=64 的 nsys 時間軸顯示 fused GEMM 的計算全部發生在最後一筆 copy 之後。
4. **地圖不單調。** G-FC1 與 L-GU 在特定 M 有「斷崖」，Flux fused 在那裡突然變差：
   - 上游 registry 的 config 在本機很差：G-FC1 M=1024、L-GU M=4096；
   - 沒有 registry 條目時的 fallback 很差：G-FC1 M=3072，fused kernel 本身病態，比串行還慢 0.53 ms。
5. **決策器用「每層查表」就夠。** 在 decode / prefill / 混合三種 trace 上：
   - π_lut 與 oracle 的差距（regret）為 **0–2.0%**；
   - 「永遠開 Flux」為 decode 32–108%、混合 6–24%；
   - 查表開銷 0.24 µs/次。
   - G-QKV、L-QKV 為 0%；L-GU ≤ 0.94%；G-FC1 1.6–2.0%，原因是 M=3072 斷崖不在查表網格內。
   - 所以查表必須在**部署時實際會出現的 M**上量測建立，不能從網格內插。
6. **要不要改 Flux 程式碼（D-006）。**
   - decode 區**不值得**：調 GEMM config 上限只有 ≤ 6%，off 仍快 18–139%。
     損失是結構性的（AllGather 固定成本），不是 config。
   - 只有少數中段斷崖點值得：G-FC1 M=3072、L-GU M=4096，調好後 fused 可再比 off 快 9–17%（估計）。
   - 建議先不改，詳見第 5 節。

## 2. 歸因（E2）

### 2.1 三項分解（design 6）

每點每項都是同輪交錯量測後逐輪相減的中位數。三項相加與 t_A − t_B 相差 < 10% 的點：**156/160**。
4 個例外的 |t_A − t_B| 只有 12–30 µs，絕對偏差 2–4 µs。

M ≤ 512 的 11 個點，gpu 模式，取中位數（ms）：

| 層 | A − B | C − B（Flux AG − NCCL AG） | D − C（Flux GEMM − cuBLAS） | A − D（overlap 收益） | Flux AG | NCCL AG |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| G-FC1 | 0.068 | 0.058 | 0.017 | −0.013 | 0.111 | 0.057 |
| G-QKV | 0.072 | 0.058 | 0.018 | −0.014 | 0.109 | 0.056 |
| L-QKV | 0.086 | 0.064 | 0.038 | −0.014 | 0.106 | 0.050 |
| L-GU | 0.069 | 0.063 | 0.011 | −0.014 | 0.106 | 0.050 |

steady 模式同結構（`results/e1_map_v2` 同表）；其中 NCCL AG 更快，0.030–0.037 ms。

**各路徑的時間下限。** 所有層在 M ≤ 64 時：Flux AG 0.100–0.109 ms，NCCL AG 0.031–0.051 ms。

### 2.2 時間軸（nsys，design 5.5）

G-FC1，device 0，每項 20 次，`results/e2_nsys/parse_G-FC1.txt`。GPU 工作透過 API correlationId 歸到 NVTX range。

| M | Flux AG launch 數 | shard copy 起訖 | fused GEMM kernel 長度 | 最後一筆 copy 後 GEMM 仍在跑 | 單獨 GEMM |
| ---: | --- | ---: | ---: | ---: | ---: |
| 64 | 2 kernel + 8 memcpy + 1 memset | 113 µs | 212 µs | **132 µs** | 125 µs |
| 1024 | 同上 | 258 µs | 1178 µs | 969 µs | 1120 µs |
| 3072 | 同上 | 429 µs | 2713 µs | **2319 µs** | 1734 µs |
| 4096 | 同上 | 529 µs | 2772 µs | 2284 µs | 2214 µs |

各點的解讀：

- **M=64**：最後一筆 copy 後 GEMM 仍跑 132 µs，≥ 單獨 GEMM 的 125 µs。GEMM kernel 雖然提早 launch，
  但 copy 期間只在等 signal，**沒有做有用的計算**。這驗證了 design 3.2：M=64 的 tile 高度 64，只有一列 tile，每個 tile 等全部 shard。
- **Flux AG 的 8 筆 copy 在同一 stream 串行**：1 local + 7 peer，M=64 時每筆約 14 µs。這就是 0.1 ms 下限的來源
  （`src/coll/ths_op/all_gather_op.cc:553-576`）。
- **M=1024**：fused 比串行 D 快 146 µs，有部分 overlap。但 registry 的 GEMM config 很慢
  （E1：Flux GEMM 0.947 vs cuBLAS 0.601 ms），所以仍輸 B。
- **M=3072**：最後一筆 copy 後 GEMM 還要 2319 µs，比單獨 GEMM 的 1734 µs 多 585 µs。
  **fused kernel 在資料到齊後仍比同一 kernel 單獨跑更慢**，與 E1 的 A − D = +0.53 ms 一致。
  **[推論]** 原因：fallback config 是 StreamK，partial tile 以 turnstile 順序等前一個 peer
  （`src/ag_gemm/sm80_all_gather_gemm.hpp:705-711`），加上等 shard 的延遲後被串行化。
  驗證：diag-overlap 的 kernel 內 `%globaltimer` 計時。
- **限制**：probe 內各項是分塊依序跑，不是交錯，所以跨項比較 kernel 長度含 clock 漂移。
  M=4096 的「最後一筆 copy 後 vs 單獨 GEMM」因此不可靠。同項內的量（copy 起訖、launch 數）不受影響。

## 5. 要不要改 Flux 程式碼（D-006）

1. **decode 區（M ≤ 512–1032）：不值得為開關決策改 Flux。**
   - 就算把 GEMM 調到最好（上限 ≤ 6%），甚至把 GEMM 做到跟 cuBLAS 一樣，Flux AG 的約 0.1 ms 下限仍比 NCCL 慢 0.05–0.07 ms。
   - 在這區直接走 NCCL+cuBLAS，不需要改任何 Flux 程式碼，決策器就能拿到全部收益。
2. **中段斷崖（少數 M）：A\*（改 pybind 暴露 hparams 並 rebuild，或把調好的 config 寫進 tuning_config 再 rebuild）有中度價值。**
   - 在 G-FC1 M=3072、L-GU M=4096，估計可比目前的最佳 off 再快 9–17%；G-FC1 M=1024 可把差距從 44% 縮到 8.5%。
   - 影響只在少數 M，且目前的查表已經能避開這些點的最壞情況（改走 off）。
   - **建議：等確定部署的 M 桶與模型形狀後，再只針對那些桶做。**
3. **若要讓 Flux 在小 M 也有競爭力**，要改的是 AllGather 本身（例如把 7 筆串行 copy 換成單一 kernel）。
   **[推論]**：這是另一個工作項目，不屬於決策器。

## 6. 限制與下一步

- **只做了 AG+GEMM**：GEMM+RS（design E5）尚未量。推論的每個 Transformer block 兩者都有，決策器要兩側都有地圖。
- **CUDA graph 相容性未驗證**（design E4）。gpu 模式只是「近似」graph 重放；Flux 路徑能否 capture 未知。
- **只有單一機器、單一 dtype（bf16）、TP=8**；換機器或 TP 要重建地圖。
- **nsys 只做了 G-FC1**；probe 不是交錯量測。
- **尚未經 auditor 審查**。本報告的結論在審查前不進 DECISIONS.md（D-004）。
