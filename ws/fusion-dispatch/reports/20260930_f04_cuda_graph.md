# F0.4：各路徑能否錄進 CUDA graph

日期：2026-09-30 · 作者：fusion-dispatch（boss session 兼 worker）

| 項目 | 內容 |
| --- | --- |
| 腳本 | `scripts/graph_capture_v1.py`、`scripts/run_f04_graph.sh` |
| 原始輸出 | `results/f04_graph/*.json`、`log_*.txt` |
| 形狀 | Llama-3-70B TP=8：AG 側為 L-QKV（N=10240, K=8192），RS 側為 L-O（N=8192, K=8192）；M ∈ {64, 1024}；bf16 |

方法：

1. 每條路徑各開一個 process。
2. 先跑 eager 取參考輸出。
3. 照 PyTorch 文件的做法，在 side stream 上 warmup 3 次，再 capture。
4. 重放 3 次，與 eager 比對：allclose，並另記是否 bitwise 相同。
5. eager 與重放交錯計時，各 100 輪。每次前清 L2、GPU 端對齊，取逐輪 rank-max 中位數。
   eager 用 gpu 模式，也就是 CPU 領先的 GPU 執行時間。

## 解讀

1. **Flux AGKernel（AG+GEMM fused）不能 capture。** 錯誤是 `capturing stream has unjoined work`。
   M=1024 的錯誤是第一次失敗後 allocator 狀態殘留的連鎖反應。

   **[程式碼]** 原因在 `forward_impl`（`src/ag_gemm/ths_op/all_gather_gemm_op.cc:271-276`）：
   - 主 stream 記錄 `ready_event`，`cp_stream` 等它；
   - `ag_op.run` 在 `cp_stream` 上執行；
   - 主 stream 只等 `local_prepare_event`，也就是 local copy 完成。

   之後在 `cp_stream` 上的 7 筆 peer copy **從未 join 回主 stream**。
   eager 時靠 GEMM kernel 內的 signal 等待保證正確，但 graph capture 要求所有 fork 出去的工作都 join 回來。

   **[推論]** 修法約 3 行：`ag_op.run` 後在 `cp_stream` 記錄一個 event，主 stream 在 **launch GEMM 之後**才等它。
   這樣不影響 overlap，且可以 capture。屬於改 `src/`，需過 D-007 的關卡。

2. **其餘五條路徑都能 capture，重放 bitwise 正確**，包含 Flux GemmRS 和「Flux AllGatherOp + cuBLAS」。
   AllGatherOp 在呼叫端的 stream 上執行，沒有 fork。

3. **graph 重放比 gpu 模式 eager 慢一點，而且對 NCCL 路徑不利較多**：
   - NCCL 路徑 +7 ~ +15 µs；
   - Flux GemmRS +2.6 ~ +4.1 µs。

   所以 gpu 模式只是 graph 的近似，對 NCCL 偏樂觀約 10 µs。
   **用 graph 部署時，決策表應直接用 graph 重放時間校準**，不要用 gpu 模式的 eager。

## 對決策器與 vLLM 整合的影響

- vLLM 預設只對 decode 的 batch 大小錄 graph，M 較小 **[推論，F4 讀原始碼確認 capture size 上限]**。
  E1 顯示 M ≤ 512–1032 的 AG 側本來就選 NCCL，所以 **AGKernel 不能 capture 在 decode 區不影響決策**。
- Flux 勝出的大 M（prefill）走 eager，不需要 graph。
- RS 側的 Flux GemmRS 能 capture。若 E5 顯示它在 decode 區也會勝出，graph 模式可以直接用。
- 只有當某個 graph 桶的 AG 側 Flux 會勝出時，才需要修第 1 點。修之前先看 E5 與 F1 的表裡有沒有這種桶。
