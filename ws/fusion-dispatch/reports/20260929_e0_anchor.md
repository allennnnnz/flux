# E0：harness 驗證、錨點、cuBLAS 設定缺陷

日期：2026-09-29 · 作者：fusion-dispatch（boss session 兼 worker）

- 腳本：`scripts/dispatch_map_v2.py`（v1 已撤回，見 1）、`scripts/analyze_v1.py`、`scripts/run_e0.sh`
- 原始輸出：`results/e0_anchor_v2/`（raw_*.csv 逐輪、meta_*.json、log_*.txt、summary_*）
- 撤回版的輸出：`results/e0_anchor/`，保留供稽核

方法：8× A100，bf16，TP=8，All2All + `use_read`。每個 (層, M) 先做正確性檢查，再做 200 輪。
每一輪把 8 個待測項以隨機順序各跑一次，順序全 rank 一致；每項前先寫 128 MB 清掉 L2。
每輪各 rank 的時間先取 rank-max，再取中位數。SM clock 取樣 20 ms，丟棄 < 95% 眾數的輪次。
三種時間模式的定義見 `dispatch_map_v2.py` 開頭。

---

## 1. 發現：Flux 的測試初始化把 cuBLAS 放在非 production 狀態

`flux.testing.initialize_distributed()` 會呼叫 `init_seed()`（`python/flux/testing/utils.py:49-62`），
它做了三件事：

- 設 `CUBLAS_WORKSPACE_CONFIG=:16:8`；
- 開 `torch.use_deterministic_algorithms(True, warn_only=True)`；
- 關掉 bf16/fp16 reduced-precision reduction。

vLLM 等服務框架三者都不設。這些設定只影響 cuBLAS 路徑（B、C、c_cublas），Flux kernel 與 NCCL 不受影響。
因此 **v1 的比較對 Flux 有利**。

以單卡、單 process 分別量每個設定（`results/e0_anchor/cublas_settings_v1.txt`，
`scripts/cublas_settings_v1.py`；每個設定獨立 process；GPU 時間為冷 L2、200 次中位數）：

| 設定 | torch.mm host launch | GPU 時間變化（相對 default） |
| --- | ---: | --- |
| default | 13 µs | — |
| deterministic（warn_only） | 17 µs | ±1% |
| `CUBLAS_WORKSPACE_CONFIG=:16:8` | **71 µs** | −4% ~ +6% |
| bf16 reduced-precision reduction 關 | 13 µs | L-GU M=512 **+26%**（319 → 401 µs） |
| 三者全開（= init_seed） | 70 µs | P0-4096 M=1024 **+26%**、L-QKV M=64 **+25%**、G-FC1 M=64 −9% |

多 process 下的旁證（`results/e0_anchor/launch_overhead_dist_v1.txt`）：在 torchrun 下，
Flux op 建立之前 torch.mm 就是 70 µs，與單 process 同設定一致，與 Flux 無關。

在 8 卡 harness 內的影響（v1 → v2，gpu 模式，c_cublas 中位數）：

| 形狀 | v1 | v2 |
| --- | ---: | ---: |
| P0-4096 M=4096 | 0.301 ms | 0.223 ms |
| P0-8192 M=4096 | 0.594 ms | 0.418 ms |
| P0-4096 M=16384 | 0.892 ms | 0.776 ms |
| G-FC1 M=4096 | 2.501 ms | 2.502 ms（不變） |

P0-4096 M=4096 的判決因此改變：v1 是「fused 快 12%」，v2 是**平手**。

**處置**：

- `dispatch_map_v2.py` 在 `initialize_distributed()` 之後、第一次 cuBLAS 呼叫之前，恢復 PyTorch 預設，
  並把有效設定寫進 meta。v2 的 meta 記錄為 `CUBLAS_WORKSPACE_CONFIG=None`、`deterministic=False`、
  `allow_bf16_reduced_precision_reduction=True`。
- v1 加 WITHDRAWN banner。
- v2 裡 c_cublas 的 host launch 回到 14–17 µs（steady 模式）。

**波及範圍**：任何透過 `flux.testing.initialize_distributed()` 跑的「Flux vs torch」比較，
torch 那一側都受這個影響，包含上游 `test_ag_kernel.py` 的 torch 列。Phase 0 的 AG+GEMM
只比 Flux 自己的 kernel，E.3 的「torch 約 3.30 ms」本來就沒被引用，所以 Phase 0 結論不受影響。
**建議 boss 把這條加進 `CLAUDE.md` 陷阱表。**

## 2. 錨點（design 5.4）

v2，200 輪，括號內為 modal SM clock：

| 錨點 | Phase 0 | gpu 模式 | host 模式 | steady 模式 | 偏差（gpu） |
| --- | ---: | ---: | ---: | ---: | ---: |
| fused, M=4096, N=4096 | 0.736 | 0.681 (1410) | 0.694 | — | −7.5% |
| fused, M=4096, N=8192 | 0.677 | 0.645 (1410) | 0.664 | — | −4.8% |
| fused, M=4096, N=49152 | 2.747 | 2.548 (1350) | 2.583 | 2.691 (1200) | −7.2% |
| gemm_only, N=4096 | 0.278 | 0.242 | 0.266 | — | −13% |
| gemm_only, N=8192 | 0.564 | 0.479 | 0.504 | — | −15% |
| gemm_only, N=49152 | 2.562 | 2.302 | 2.367 | 2.436 | −10% |
| Flux AG, M=1024 / 4096 / 16384 | 0.199 / 0.468 / 1.668 | 0.215 / 0.477 / 1.481 | 0.228 / 0.485 / 1.495 | — | +8% / +2% / −11% |
| NCCL AG, M=4096 | 0.569 | 0.478 | 0.509 | — | −16% |

全部在 20% 內。5–20% 的偏差如下：

- **gemm_only −10% ~ −15%：SM clock。** 本次短 run 在 1410 MHz，Phase 0 記錄 1155–1200 MHz。
  1177/1410 = 0.835，預期 −16%。steady 模式在持續負載下降到 1170–1245 MHz（功耗上限 400 W，未設 cap），
  此時 G-FC1 的 fused 與 gemm_only 距 Phase 0 只有 −2.0% 與 −4.9%。
  **Phase 0 的數字是在持續負載的功耗上限下量的**；gpu 模式的 sleep pad 讓 GPU 降溫降功耗，clock 較高。
  推論時是持續負載，所以最終判決以 steady 模式的 clock 條件為準，gpu 模式當作 GPU 純執行時間的參考。
- **NCCL AG −16%：與 clock 無關，一部分來自協定。**
  - 同一 run 內 host barrier 對齊量到 0.509，GPU 端對齊量到 0.478：host skew 讓 NCCL 多算 6%。
  - 其餘 10%（0.509 vs 0.569）**未解釋**。Phase 0 E.1 是 20–30 次、per-rank 中位數再取 rank-max、fp16；
    本次是 200 輪、逐輪 rank-max 再取中位數、bf16，bytes 相同。

## 3. 發現：Phase 0「Flux AG 比 NCCL 快 13–22%」在 M ≤ 4096 不成立

同一 run、同一輪內交錯量測：

| M | Flux AG | NCCL AG | 比值（gpu） | 比值（host） | Phase 0 E.1 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64（K=12288） | 0.109 | **0.052** | NCCL 快 2.1× | NCCL 快 1.4× | — |
| 1024 | 0.215 | **0.181** | NCCL 快 16% | NCCL 快 4% | Flux 快 13% |
| 4096 | 0.477 | 0.478 | 相同 | Flux 快 5% | Flux 快 22% |
| 16384 | **1.481** | 1.734 | Flux 快 15% | Flux 快 15% | Flux 快 16% |

只有 M=16384 重現 Phase 0。Phase 0 的比較不是交錯量測，且用 host barrier；
本次 host 模式也只有 5%，所以差異不全是協定造成。

**[程式碼]** 小 M 時 Flux AG 慢的原因：All2All 在**同一條 stream 上串行**發 7 筆 `cudaMemcpyAsync`，
每筆後面一個 `set_ready`（`src/coll/ths_op/all_gather_op.cc:553-576`）；
前面還有兩次 barrier、一次 memset、一次 local copy（`all_gather_op.cc:410-456`）。
小 M 時這些固定成本主導，NCCL 只有一個 kernel。

**需 boss 裁決**：Phase 0 E.1 / `PHASE0_FINDINGS.md` 2.6 的「在 M=1024–16384 全程快 13–22%」是否撤回或改寫為
「僅 M ≥ 16384 成立」。D-005（AG 模式選 All2All）比的是 Flux 自己的各模式，不受影響。

## 4. 協定自洽性（design 5.1、5.2）

- **gpu 模式**：composite 與元件相加的差，在所有點都 < 10%（`summary_flags.txt`）。通過。
- **host 模式**：B、C 比元件相加快 12–13%。這是**模式本身的性質**，不是量測錯誤。
  host 模式每個單項都包含一次 launch latency；composite 的第二個 launch 被第一段的 GPU 執行蓋住，所以不可相加。
  **host 模式只用於錨點**，不進決策。
- **steady 模式**：G-FC1 M=4096 因功耗上限的 clock 起伏丟掉 69/200 輪，剩 131 輪。
  短於 200 輪的點在報告中註明。

## 5. E0 的初步判決點

用 v2 資料；「off」取 B/C/D 中位數最小者；判決規則見 design 5.6。

| 層 | M | 模式 | fused | 最佳 off | Δ(A − off) p10 / 中位數 / p90 | 判決 |
| --- | ---: | --- | ---: | --- | --- | --- |
| G-FC1 | 64 | gpu | 0.230 | B 0.167 | 0.048 / 0.064 / 0.080 | **off，快 28%** |
| G-FC1 | 64 | steady | 0.212 | B 0.150 | 0.053 / 0.062 / 0.069 | **off，快 29%** |
| G-FC1 | 64 | host | 0.247 | B 0.206 | 0.029 / 0.043 / 0.058 | **off** |
| P0-4096 | 1024 | gpu | 0.292 | B 0.247 | 0.019 / 0.043 / 0.095 | **off** |
| P0-4096 | 4096 | gpu | 0.681 | B 0.697 | −0.042 / −0.017 / 0.023 | 平手 |
| P0-8192 | 4096 | gpu | 0.645 | B 0.893 | −0.276 / −0.252 / −0.210 | fused |
| G-FC1 | 4096 | gpu / steady | 2.548 / 2.691 | D 2.793 / 2.898 | 中位數 −0.243 / −0.214 | fused |
| P0-4096 | 16384 | gpu | 1.650 | C 2.257 | −0.629 / −0.607 / −0.570 | fused |

G-FC1 M=64 在三種模式下都是 off 勝，勝在兩項（分解見 design 6）：

- C − B = +0.064：Flux AG 比 NCCL 慢；
- D − C = +0.016：Flux GEMM 比 cuBLAS 慢；
- A − D = −0.014：overlap 只收回 0.014。

這符合 design 3.2 的預測：M=64 的 tile 高度是 64，只有一列 tile，每個 tile 都要等所有 shard。
**[推論]**，nsys 驗證排在 E2。

## 6. 結論

- harness 可用：錨點全部在 20% 內且偏差有解釋，gpu 模式自洽。
- **v1 撤回**：cuBLAS 設定缺陷，影響 B/C 達 13–35%。
- 可以進 E1。
